# RAG 版本发布与反馈回流 SOP

> 实验记录：保留本轮操作、观察与结果，不作为通用操作入口。通用步骤见 [开发 SOP](../sop/README.md)。

适用范围：本项目 Dify 本机开发应用。供开发人员在生成基线和单项回归之后执行；不能代替公司内网部署、业务验收或正式运维方案。

**当前状态：单项 Prompt 回归、拒绝候选、原版恢复、DSL 导出与独立副本真实恢复验证已完成；原发布网页四次新请求后台核查已完成，于 2026-10-16 经人工确认“页面显示正常”。** 实测证据见第 7 节，不将接口验证替代网页验收。主入口为[开发闭环](栈问答开发闭环实验记录.md)。

## 1. 以一次改动形成可比较的候选

前置输入：`stack-generation-v0` 题集、当前版本真实 API 运行目录及人工标注、完整非凭据配置快照。新运行必须使用同一入口，不把网页预览、发布网页和 API 的延迟直接混算。

1. 从[人工标注问题](生成评测记录.md)选 `GEN-S02-001` 和同类的 `GEN-S03-002`，目标为减少主动概括导致的条件遗漏；`GEN-S03-001` 用于观察无依据补充是否改善。
2. 将原完整 Prompt 保存为 `grounded-rag-v1`；编排页仅修改 Prompt，拟定版本 `grounded-rag-v2`。不要同时改变文档、模型参数、Top K 或权重。
3. v2 强调只回答所问、资料没展开的实现不补充、主动比较时带上影响结论的条件；不得加入测试题专用答案或仅为过关的题号规则。
4. 保存完整候选配置，发布后刷新核查，再使用同一 API 题集新建运行。候选发布是本机开发验证，不代表正式准出。
5. 逐轮人工标注，比较目标问题与原本正确的定义、操作、拒答和追问。收益报告给具体计数和原句，不只报平均分。
6. 有改善且无关键退化时保留；无改善、出现退化或证据不足时回退并如实记录。一次采样的变化不证明稳定改善；本轮只验证开发闭环。

输出：新旧 Prompt、配置差异、两个真实运行目录、人工对比和保留／回退决定。完整实际上下文缺失时仍明确保留未知，不用好答案填补 Trace 缺口。

## 2. 固定发布记录

建立一份版本说明，至少包含：

| 字段 | 填写内容 |
|---|---|
| 版本与入口 | 候选号、应用 ID、实际网页入口和 API 入口 |
| 依赖版本 | Dify、模型名与 digest、Embedding、资料 SHA-256、题集 SHA-256 |
| 应用配置 | 完整 Prompt、生成参数、知识库与应用两层检索设置、引用开关 |
| 效果证据 | 基线运行目录、候选运行目录、人工标注与选择理由 |
| 已知问题 | 未解决的质量、展示、性能与 Trace 缺口及影响 |
| 恢复依据 | 前版本配置、DSL 文件、恢复执行记录 |

Dify 应用菜单导出 DSL，先检查凭据和不适合分享的信息再入项目。DSL 只是应用配置，不能恢复知识库数据、向量索引、模型权重、数据库或插件凭据；另保留非凭据快照和资料版本。

## 3. 发布与实际入口验收

1. 编排页确认候选配置，点击“发布 → 发布更新”。
2. 刷新编排页，再核对模型、Prompt、资料引用和参数。记录核对时间与配置文件。
3. 从“发布 → 运行”打开真实发布网页，有答案 S01、无答案 S04、M01 两轮各执行一次。每组新会话，多轮组内部不新建会话。
4. 保存问题、完整回答、来源及会话身份；截图只记录关键区域，长输出另存文本。拒答仍出现候选引用时照实记录。
5. 发布网页与 API 结果不一致时，先核对是否同一个应用和已发布版本；不得仅凭“发布成功”认定行为一致。

输出：发布配置刷新核查与实际网页四次真实请求。此处复用开发题属于部署回归，不是独立业务验收。

## 4. 验证恢复

优先在独立测试副本验证，不覆盖唯一可用应用：

1. 通过 Dify 的 DSL 导入功能创建临时应用，导入上一版本；核对知识库绑定、模型 Provider、插件依赖与参数。导入提示缺依赖时先补齐或停止，不能声称恢复成功。
2. 运行 S01，保留实际回答与来源，确认副本能真实执行前版本链路。
3. 将副本配置与上一版快照比较，记录不一致项。原发布应用继续保留选定版本。
4. 若将来必须回退原应用：使用留存配置或导入经验证 DSL 恢复，再发布、刷新核查，并重新执行有答案、拒答与多轮检查。副本成功只是恢复演练，不代表原应用已发生回退。

输出：副本身份、导入来源、配置核查和真实推理证据。仅有 DSL 文件不算恢复验证。临时应用是否删除由操作人员决定，不自动清理。

## 5. 把反馈接回测试与发布

复用本轮质量反馈，不再制造额外实验。维护下表的真实状态：

| 反馈 | 测试／判断条件 | 处理路径 |
|---|---|---|
| 复杂度条件遗漏 | S02、S03、M01 的 conditional_constraints | 关联 Prompt 单项改动、同题回归与发布版；失败则保留未解决 |
| 无资料支持的扩充 | S03 分配／复制解释与原文逐句核对 | 与同轮回归对照，不把一般知识正确等同于资料支持 |
| 拒答仍显示无关引用 | S04 发布页拒答与来源状态 | 展示待办，不强行用 Prompt 保证前端行为 |
| 慢请求与页面可读性 | 已有多轮计时、截图与排查记录 | 独立待办，本轮质量改动不冒充解决性能或 UI |

每条已处理反馈保留“反馈证据 → 回归题及预期 → 改动版本 → 真实运行 → 判断 → 发布版本”。至少一条走到处理决定与发布关联才可称本轮反馈回流已验证。改动无效并回退也可说明处理路径已执行，但不能把原质量问题标记为已解决。

## 6. 完成时检查

开发闭环的八个环节逐项链接到真实产物；将确定性测试、真实推理成功、人工质量结论、待核查项分开报告。没有完成的步骤保留未执行，不通过填写模板替代执行。正式 IT 系统的业务标准、文档权限、人工接管与运维仍需另行验收。
