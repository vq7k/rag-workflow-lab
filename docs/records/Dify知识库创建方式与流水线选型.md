# Dify 知识库创建方式与流水线选型

> 实验记录：保留本轮操作、观察与结果，不作为通用操作入口。通用步骤见 [开发 SOP](../sop/README.md)。

核对日期：2026-10-15。对应本地部署：Dify 1.13.0。本文依据官方中文自部署文档，并对照官方英文模板说明及本地源码。官方在线文档持续更新，菜单名称、模板列表和插件能力不一定与本地版本完全一致。

## 1. 三个入口分别解决什么问题

创建知识库需要解决两件事：文档如何变成可检索的数据，以及用户提问时由谁执行检索。Dify 的三个入口对应不同的管理边界。

| 页面入口 | 官方文档名称 | 文档处理与索引由谁管理 | 主要配置内容 | 适用情况 |
|---|---|---|---|---|
| 创建知识库 | 创建即用型知识库 | Dify | 数据源、清理、分段、索引和检索参数 | 标准文档，先验证基本 RAG 流程 |
| 通过知识流水线创建知识库 | 构建自定义知识库 | Dify；处理过程由操作人员编排 | 数据源节点、提取器、分块器、模型处理和知识库节点 | 需要更换解析器、加工内容或复用处理流程 |
| 连接外部知识库 | 连接外部知识库 | 外部检索服务 | 外部服务地址、认证、知识库 ID 和检索参数 | 已有自建 RAG 或第三方知识服务 |

前两个入口都是在 Dify 内管理知识内容与索引，区别主要在于处理流程的配置方式。第三个入口把检索交给外部服务，Dify 接收检索结果供应用使用。

知识库负责提供检索内容。创建知识库、发布知识流水线，不等于已经创建或发布员工使用的问答应用；回答生成、引用展示、拒答和转人工仍需在应用中设计。

## 2. 直接创建知识库：配置现成的处理流程

典型过程：

```text
上传文档或选择数据源
  → 配置清理与分段，查看预览
  → 选择索引方式、Embedding 模型与检索设置
  → Dify 执行处理并建立索引
  → 在检索测试中检查命中内容
```

以《栈》为例：上传 `stack.md`，设置分隔符、分段长度等参数，预览哪些文字会被切到同一块，再由 Dify 完成入库。选择高质量索引和 BGE-M3 时，Dify 会调用模型生成向量，并将索引写入配置的向量存储；本机部署使用 Weaviate。

这一路径已经包含文档解析、清理和分段，不要求先写本地脚本重复实现整套入库流程。本地脚本用于理解和对照验证，是否需要预处理取决于导入后的实际内容。对当前样本，应检查图片相对路径、代码引用和模板语法是否留下无意义内容或造成信息缺失。

直接创建也支持分段与检索策略选择，并非所有文档都只能按固定长度切块。它提供标准配置入口；知识流水线进一步开放处理节点与连接方式。

## 3. 通过知识流水线创建：编排文档处理过程

官方将知识流水线划分为四个环节：

```text
数据源 → 数据提取 → 数据处理 → 知识库存储
```

一个具体流程可以是：

```text
上传 Word → 文档提取器 → 转为 Markdown → 父子分块器 → 知识库节点
```

各环节职责如下：

- **数据源**：接收本地文件，或通过连接器获取网页、在线文档、网盘文件。
- **数据提取**：将文件格式转换为可处理的正文、表格等内容；复杂布局可能需要专门解析插件。
- **数据处理**：清理、分块、提取表格中的问答列，或通过 LLM 生成问答对、补充上下文。
- **知识库节点**：接收符合结构要求的分块，设置分段结构、索引方式和检索策略。

先编排和测试，再发布流水线，之后通过已发布流程导入资料。流水线发布的是处理配置；实际文档仍需运行处理才能入库。连接了数据源也不代表已具备定时同步或删除同步，需另外核对连接器和调度能力。

### 3.1 流水线的创建来源

这里的分类说明“配置从哪里来”，不说明检索采用哪种算法：

| 来源 | 含义 |
|---|---|
| 空白流水线 | 自行选择节点并连接，适合已有明确处理需求 |
| 内置模板 | 采用平台提供的节点组合，再检查并修改参数 |
| 自定义模板 | 复用工作空间内保存的处理方案 |
| 导入 DSL | 通过 YAML 配置复用已有流水线；仍需检查插件、凭据及模型依赖 |

使用模板并不保证依赖已安装或配置可直接运行。模板是起点，需要查看其节点、模型、分段和索引设置。

### 3.2 三种分段结构

这是“入库数据如何组织”的分类，与模板来源是两个维度。

| 结构 | 如何索引和返回内容 | 示例与适用情况 |
|---|---|---|
| 通用模式 | 将正文拆成单层分块，匹配后返回对应分块 | 独立的概念说明、短操作步骤；适合作为当前基线 |
| 父子模式 | 小的子块参与匹配，命中后返回对应的大父块作为上下文 | 子块为“VPN 错误码说明”，父块包含完整排障步骤及适用条件 |
| 问答模式 | 按问题部分建立索引，匹配后返回关联答案内容 | 从 FAQ 表格提取“问题—答案”，或由 LLM 从原文生成问答对 |

父子模式并不是先查父块再查子块。其主要作用是让匹配粒度与返回上下文粒度分开。问答模式改变了知识的表示方式，仍不等于最终应用只能原样返回答案。

分段结构会影响后续管理和检索；官方说明保存发布后不能随意切换。比较通用与父子模式时，建议分别创建实验知识库，使用同一批文档和问题对照。

### 3.3 索引方式与检索策略

这是“如何建立索引、如何查找内容”的分类，不是另一组流水线类型。

- **高质量索引**：调用 Embedding 模型建立向量索引，支持向量、全文或混合检索设置。名称不代表效果已经验收。
- **经济索引**：基于关键词和倒排索引，不执行本阶段需要验证的 BGE-M3 向量化链路。
- **向量检索**：根据问题与资料的语义向量检索相关内容。
- **全文检索**：根据词项匹配检索，适合关注产品名、术语、错误码等内容。
- **混合检索**：结合语义与词项检索；融合权重或 Rerank 配置需结合实际版本与模型能力检查。

通用结构支持高质量和经济索引；父子、问答结构使用高质量索引。**通用模式不等于经济索引**：只是某些通用模板默认采用经济索引。

## 4. 常见内置流水线模板的区别

下面按官方模板专题解释处理目的。模板默认配置可变，不应把模板名当作固定的算法或必然优于其他模板的质量等级。

| 模板名称 | 核心处理过程 | 主要适用资料 | 选择时检查 |
|---|---|---|---|
| General Mode-ECO／通用模式 | 文档提取 → 通用分块 → 经济索引 | 简单正文、关键词检索实验 | 默认不调用 Embedding，不能用于验证 BGE-M3 入库 |
| Parent-child-HQ／父子模式 | 文档提取 → 父子分块 → 高质量索引 | 长操作手册、上下文相关的技术资料 | 父子块边界、返回内容长度、Embedding 和检索设置 |
| Simple Q&A／简单问答 | 从表格选定问题列和答案列 → 问答分块 | 已有 CSV、Excel FAQ | 列映射、空值、重复问题；不依靠 LLM 编写答案 |
| LLM Generated Q&A／LLM 生成问答 | 从原文调用 LLM 生成问答对 → 问答分块 | 缺少标准 FAQ 的叙述性文档 | 生成模型可用性、遗漏和幻觉；生成答案需核对原文 |
| Convert to Markdown／Markdown 转换 | Office 文档转换 → 分块与索引 | DOCX、XLSX、PPTX 等原生文件 | 格式转换是否保留结构；官方不推荐将其用于 PDF |
| Complex PDF with Images & Tables／复杂 PDF | 专门解析 PDF 的图文和表格 → 分块与索引 | 排版复杂、包含图表的 PDF | 解析插件依赖、表格和阅读顺序；扫描件还需确认 OCR 能力 |
| Contextual Enriching Using LLM／LLM 上下文增强 | 提取图文表格 → LLM 生成描述性上下文 → 分块与索引 | 纯文本提取不足以表达含义的图表资料 | 解析和生成模型依赖，描述是否忠实于原文 |

前两类主要改变分块与索引；中间两类改变知识的问答表示；后三类主要解决格式解析和内容增强。一条流水线可以同时包含这些处理步骤，分类不是互斥的。

中文官方模板页当前列出上述七类，英文对应页列出其中五类；本地模板清单也存在解析异常，不能据此确认七类在本地均可使用。**实际可用模板以本地页面、模板详情和插件依赖为准。** 本文中的七类用于解释处理目的，不是本机已验证清单。

图片解析、LLM 生成图片描述和图片向量化是不同能力。当前 BGE-M3 是文本 Embedding 模型；选择复杂 PDF 或增强模板，不会自动让它具备图像理解能力。

## 5. 连接外部知识库：通过 API 调用已有检索服务

典型边界：

```text
外部系统：文档采集 → 解析 → 分块 → 索引与内容维护
                                       ↑
Dify 应用：用户问题 → 外部检索 API → 返回内容片段 → LLM 生成回答
```

外部服务可以使用自己的模型、向量数据库、权限过滤和检索逻辑。Dify 不负责管理外部文档的上传、修改、删除和索引更新，而是在提问时调用其检索 API。

连接分为三个步骤：

1. 外部系统提供符合 Dify 协议的检索 API，或使用适配已有服务的插件。
2. 在“外部知识库 API”中注册服务基础地址和认证信息。
3. 点击“连接外部知识库”，选择 API，填写外部知识库 ID 和检索参数，再供应用使用。

根据官方 API 文档，Dify 请求 `POST {基础地址}/retrieval`，请求包含 `knowledge_id`、`query` 和 `retrieval_setting`（如 `top_k`、`score_threshold`）。服务返回 `records` 数组，每条包含检索内容 `content`、分数 `score`、标题 `title` 和对象类型的 `metadata`。

这里返回的是供模型使用的知识片段，不是直接用任意聊天接口返回一段最终答案。已有向量数据库也不意味着可直接连接：通常仍需检索 API 适配层。

**外部数据源不等于外部知识库。** 从 Notion 或网页读取内容后在 Dify 内入库，属于前两个入口；文档及索引留在外部系统，Dify 每次提问调用其检索接口，才属于外部知识库。

## 6. 当前项目如何选择

当前目标是理解并验证全文解析、切块、BGE-M3 向量化入库和检索。先采用：

**直接创建知识库 → 一篇《栈》文档 → 通用分段 → 高质量索引 → BGE-M3 → 向量检索。**

这条路径减少其他处理变量，便于把切块内容、实际索引和检索结果与已有本地演示对应起来。先查看分段预览，确认正文可用；本次文档整理不执行入库或模型调用。

后续选择由问题驱动：

- 命中片段缺少步骤前提和上下文：对照父子模式。
- 数据是经过确认的问答表：考虑 Simple Q&A。
- 原文解析失败或确有特定加工需求：考虑知识流水线及对应解析模板。
- 公司已经建设独立知识检索服务：评估连接外部知识库。

公司 IT 服务台约 200–300 篇文档，数量本身不足以决定采用哪个入口。主要依据是格式与内容结构、更新方式、检索控制需求，以及谁负责维护知识与索引。知识流水线不必成为必经的“高级阶段”。
