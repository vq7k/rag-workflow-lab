# 08 反馈与排障

输入：实际问答反馈、错误或慢请求，以及对应版本。

输出：可关联的问题、分层证据、处理决定与回归条件。

## 反馈回流

1. 保存问题原文、必要历史、实际回答、预期、入口、时间和消息／会话 ID；反馈来源注明测试观察或真实使用，不混写。
2. 检查原文是否含答案，再核查实际检索上下文，最后检查生成与展示。无依据时记录未知，不直接归因模型。
3. 分类为资料、分块／检索、生成、会话、性能、展示或权限问题，写清证据和下一步动作。
4. 把可复现问题转为有来源、条件和禁止结论的回归用例，版本化题集；独立验收集不要随调优反复修改。
5. 关联[单项改动与真实回归](06-优化与回归.md)，记录保留、拒绝、回退或待核查，关联最终发布版本。
6. 核查原问题是否真正解决。实验失败并回退时，处理过程可结束，但原质量问题保持未解决。

## 人工排障顺序

1. **锁定请求**：明确是哪一轮，保存 message ID、conversation ID、入口、时间与时区；同会话不同轮不能混为一次请求。
2. **页面与接口**：查看后台日志；前端异常查看浏览器 Console 和 Network 的错误、状态码与失败请求。导出前移除 Cookie、Authorization 和知识正文中的敏感信息。
3. **应用与插件**：在实际 Dify 部署目录核查服务状态，按目标时间窗口查看 API、worker 与插件日志。服务名和日志字段以版本及部署配置为准。
4. **模型服务**：关联 Embedding／生成调用的模型、时间、耗时、失败及加载事件，区分冷启动、排队与持续处理。仅按相近时间不能可靠关联高并发请求。
5. **归因边界**：Pipeline、插件和模型计时可能互相包含，不相加；未归因的差值不要直接命名为检索耗时。客户端总等待不是首 Token 时间。
6. **输出结论**：分别写已确认、未确认与下一步只补的证据；环境未变化时优先查已有记录，避免无理由重复模型请求。

Docker Compose 部署可先在实际部署目录执行：

```shell
docker compose ps
docker compose logs --no-color --tail 200 api
```

第二条仅适用于服务名为 `api` 的部署。进一步加 `--since`／`--until` 过滤实际窗口，避免整表或全量日志导出；数据库查询优先只读且只取目标消息字段。

## 日志与追踪边界

各服务有日志或打印 `trace_id` 不等于完整 Trace。需要实际找到同一请求的父子 Span、各阶段开始结束及错误，才能声明端到端追踪可用。

前端采集、后端关联字段、脱敏、保留期、告警和可观测平台是独立运维工作；按部署要求调研和验收，不默认已接入，也不要求为每次开发实验新增平台。

## 完成条件

- 至少一条真实问题能关联测试、处理决定、回归与发布。
- 未解决项有状态，证据不足项未伪装成根因结论。
- 排障结论可定位到目标请求，性能结论说明计时范围。
