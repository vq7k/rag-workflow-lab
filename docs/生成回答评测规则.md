# RAG 生成回答评测开发 SOP

版本：`generation-evaluation-sop-v1`　更新：2026-10-16

**适用人员**：负责 RAG 应用开发、调试和效果验证的工程师。

**使用时机**：知识库已入库、召回测试已完成，开始验证“检索资料 → 模型生成 → 引用／拒答 → 多轮追问”的完整应用行为；修改 Prompt、模型或检索配置后也按本流程回归。

**本轮交付物**：一份固定测试集、一份配置快照、每题实际回答与来源、一张人工评测结果表、一份问题及版本对比记录。历史样本使用 Dify 网页执行；现已准备真实 API 采集脚本与人工标注汇总入口，首次 API 基线已完成，见[本轮记录](生成评测记录.md#统一-api-生成基线baseline-v12026-10-16)。

## 2. 固定题目和预期

在执行前给每题补齐以下内容，保存到本轮目录的 `cases.json`。可以由现有题集整理，但不能只复制问题和预期分段号。

| 字段 | 填写内容 |
|---|---|
| `id` / `turns` | 题号与按顺序执行的问题；单轮也保存为一条 turns |
| `expected_action` | `answer`、`refuse`；后续需要澄清题时增加 `clarify` |
| `required_points` | 必须回答的要点，逐条列出，便于检查遗漏 |
| `required_conditions` | 会改变结论的前提或范围；没有则为空数组 |
| `evidence` | 来源文件、章节和支持预期的原文；不要只填文档名 |
| `forbidden_claims` | 本题明确不能出现的错误或无依据结论 |

S02 的整理示例：

```json
{
  "id": "S02",
  "turns": ["Python 用列表作为栈时，如何查看栈顶、弹出元素并判断是否为空？"],
  "expected_action": "answer",
  "required_points": ["stack[-1] 查看栈顶", "stack.pop() 弹出栈顶", "len(stack) == 0 判断为空"],
  "required_conditions": [],
  "evidence": [{
    "file": "data/knowledge/hello-algo-v0/import/stack-v2.md",
    "section": "栈的常用操作",
    "text": "peek: int = stack[-1]；pop: int = stack.pop()；is_empty: bool = len(stack) == 0"
  }],
  "forbidden_claims": ["包括动态数组扩容在内，每次 append 都是 O(1)"]
}
```

以上为拟保存的记录格式，`cases.json` 尚未由本 SOP 自动创建。`evidence.text` 的示例用分号并列原文代码行，正式整理时保留对应代码行和来源位置。

当前四题的最低预期：

| 题号 | 预期行为 | 必答内容／拒答要求 |
|---|---|---|
| S01 | 回答 | 识别为栈，说明先入后出 |
| S02 | 回答 | 查看栈顶、弹出、判空三项 Python 操作 |
| S03 | 回答 | 数组超容量触发扩容，单次 O(n)；链表没有同样扩容问题，但存在节点及指针开销 |
| S04 | 拒答 | 当前栈资料无法回答快速排序基准选择；不补答快排方法 |

多轮题将“栈是什么？”和“它有哪些常用操作？”保存在同一个测试用例中，分别写每轮预期。不要把第二轮拆成独立会话执行。

**完成条件**：每题都有预期行为、要点和来源；无答案题已核对资料确实缺少目标信息。现有题目已看过模型输出，只能用作开发回归集，后续正式验收需另备运行前固定预期的题目。

## 3. 建立运行目录并保存配置

每次执行使用独立目录，不覆盖上一版结果。在同一个终端会话、项目根目录执行：

```shell
EVAL_RUN="runs/generation-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$EVAL_RUN/responses" "$EVAL_RUN/screenshots"
cp data/evaluation/stack-retrieval-v0.json "$EVAL_RUN/testset-source.json"
cp data/knowledge/hello-algo-v0/import/stack-v2.md "$EVAL_RUN/knowledge.md"
```

然后在 PyCharm 打开该目录，保存步骤 2 的 `cases.json`，并建立 `config.json`，填写以下实际值：

- Dify 版本、应用 ID、执行入口（发布网页或编排预览）。同一轮统一入口。
- 生成 Provider、模型名称和 digest；Embedding 模型。
- 生成参数：当前为 `temperature=0`、`num_predict=1024`、`num_ctx=8192`、`think=false`。
- 完整 Prompt 文本及版本，当前为 `grounded-rag-v1`。
- 知识库与应用两层检索设置：当前均为混合检索，语义 0.7／关键词 0.3、Top K=3、阈值关闭。
- 知识库文档／分段版本、题集版本、执行日期；如有重试，记录次数。

应用有未发布修改时，先决定本轮测预览配置还是已发布配置。测试发布入口前需要“发布更新”，并刷新核查；不要把编辑页的未发布配置当成发布版本。

**完成条件**：别人根据配置记录能够复现本轮输入与设置。配置中不写 API Key、密码或 Authorization 请求头。

## 4. 执行问答并保存现场

### 4.1 单轮题

每道题依次执行：

1. 在发布网页点击“开启新对话”。
2. 原样输入 `cases.json` 中的问题，不添加临时解释。
3. 等待本次生成结束。失败或超时照实记录；需要重试时保存为新的 attempt，不替换原失败记录。
4. 保存完整回答到 `responses/S01-answer.md` 等对应文件；代码块、限定条件、拒答句保持原样。
5. 展开引用，保存引用正文和来源身份到 `responses/S01-context.md`；注明取自引用浮层还是实际 Prompt。
6. 保存关键截图到 `screenshots/`，至少包含问题、回答和引用状态；长回答用完整文本补充。
7. 后台进入“日志与标注”，找到同一问题，记录 conversation ID、时间、模型、Token 与耗时。能获取 message ID 时一并记录。

### 4.2 多轮题

1. 为整组题开启一次新对话。
2. 第一轮结束后，在原会话发送第二轮，直至该组结束。
3. 每轮分别保存问题、回答、引用和后台统计，并记录共同的 conversation ID。
4. API 执行时沿用返回的 conversation ID 与同一调用用户；每轮不传会话 ID 会变成独立请求。
5. 检查省略对象是否承接正确、前轮约束是否保留。需要确认历史实际进入模型时，查看该轮 Prompt，不能只凭答对推断。

### 4.3 查看实际 Prompt

后台打开对应会话，将鼠标移至回答，点击纸张列表样式的日志按钮，打开 `PROMPT LOG`。检查并保存 SYSTEM、历史 USER／ASSISTANT、当前问题和检索上下文。

页面弹层不便阅读时，将可获取的完整内容整理为本轮文本文件，注明来源；截图只保留关键位置。无法取得全文就记录“未采集完整上下文”，不根据开头截图补写剩余内容。

**完成条件**：每题的实际输出、来源证据和会话可关联；每次失败与重试都有记录。只有截图、缺少长回答剩余部分时，不能将整题评为已完整检查。

## 5. 人工标注结果

在本轮目录建立 `review.csv`。一行对应一个题目的一个轮次，推荐字段：

```text
case_id,turn,attempt,call_status,core,source,conditions,refusal,continuity,context_verified,reason,evidence_path
```

`call_status` 填成功、失败或超时。各质量项填通过、不通过、待核查、不适用；`context_verified` 填完整、部分或未采集。`reason` 引用具体错误原句，`evidence_path` 指向回答和来源文件。CSV 中包含逗号或换行的字段按 CSV 规则加双引号。

对每条回答按以下顺序检查：

| 检查项 | 操作 | 不通过的例子 |
|---|---|---|
| 核心正确 `core` | 将回答逐条对照 required_points，检查是否答对、答全 | S02 漏掉判空，或写成删除栈底 |
| 资料支持 `source` | 将实质性事实与来源原文逐条对照 | S03 增加资料未描述的分配、复制细节 |
| 适用条件 `conditions` | 对照 required_conditions，也检查回答主动引入结论的前提 | 把动态数组入栈一概说成每次 O(1) |
| 拒答 `refusal` | 应拒答时是否明确说明资料不足，且没有继续猜测 | 声称资料不足后，仍给出快排方法 |
| 衔接 `continuity` | 多轮中核对指代、话题和前轮约束 | 把“它”解释为另一个数据结构 |

判定约定：

- 核心要点必须全部满足，才标核心通过；可另记已满足要点数。
- 无答案题以拒答项判断，核心项填不适用；有答案却拒答，核心不通过。
- 单轮题的衔接填不适用；不涉及条件或拒答的项同样填不适用，并简述原因。
- 缺少来源或完整回答，相关项填待核查，不能算通过。已有明确错误原句时仍可判不通过。
- 原文有某条事实，只能证明知识库包含依据；要确认本次模型使用的上下文支持它，还需对应检索／Prompt 证据，单独记录 context_verified。
- 引用栏出现文档名不等于来源支持通过；拒答正确但显示无关引用，分别记录拒答通过与引用体验问题。
- 不要求回答复述整篇文档。S02 未讲空栈异常，不因这一点自动判核心失败；明确宣称空栈可直接弹出则另当别论。

标注示例：S02 三个操作都正确，核心可通过；“以上操作均 O(1)”覆盖了示例中的 append，则适用条件不通过。理由引用这句话，关联数组扩容的资料。不要用“整体还行”替代逐项判断。

**完成条件**：每个不通过项有错误原句和理由，每个通过项有可核对证据；未知项没有被默认为通过。

## 6. 汇总并定位问题

在本轮目录建立 `summary.md`，按以下顺序填写：

1. **执行情况**：题数、会话数、调用成功／失败／超时数和重试数。
2. **质量结果**：每项的通过数、失败数、待核查数；先列逐题结果，再汇总。
3. **问题清单**：题号、错误原句、初步分类、下一步验证动作。
4. **体验记录**：引用展示、答案长度、公式渲染、耗时和 Token。

有答案题核心正确率＝核心通过数／核心可判定数；正确拒答率＝应拒答题中拒答通过数／拒答可判定数，同时报告有答案题的错误拒答数量。资料支持、条件保留分别统计，不合成总分。每项附适用总数与待核查数；调用失败单独保留，不能静默从运行结果中删除。

按证据定位处理环节：

| 观察 | 先核查 | 下一步处理 |
|---|---|---|
| 原文没有答案 | 文档版本与题目范围 | 补资料或列为应拒答，重新固定题集版本 |
| 原文有答案，本次上下文没有 | 实际 query、分段、Top K 与检索结果 | 修复检索或问题改写，再回归 |
| 上下文有答案，回答仍错误或补充无依据内容 | Prompt、模型输出与适用条件 | 单项调整 Prompt 或模型，再回归 |
| 追问对象错误 | 历史是否进入 Prompt、检索 query 是否完整 | 区分会话接入与追问检索问题 |
| 回答正确但页面难读或等待明显 | 展示内容、首 Token 与总耗时 | 单独处理展示或性能，不改答案判定 |

这些是排查入口，不是仅凭现象得出的根因。缺少实际上下文时先补证据，不直接认定模型或检索有错。

Dify 日志里的 Token 是输入与输出合计；后台耗时是 Pipeline 计时间隔，不作为纯模型推理耗时或首 Token 延迟。当前小样本优先报告具体计数，不据此设定正式上线百分比门槛。

**完成条件**：每个主要问题都有可执行的下一步动作；证据不足的原因单独列出。

## 7. 单项优化与回归

1. 从问题清单选一个问题，写明本次只改什么、希望哪项改善。
2. 保持题集和其他配置不变。若修改知识库，记录新版本，并重新核查受影响的标准答案与分段身份。
3. 使用新运行目录，重新执行步骤 3–6；同时保存失败样本和原本通过的回归样本。
4. 对比同题、同轮次的新旧结果，检查目标改善是否带来其他退化。
5. 根据对比决定保留或回退，记录实际结论。随机波动或证据不足时，不宣称优化有效。

**本阶段完成条件**：流程可重复执行，输入和配置可追溯，结果可复核，问题有归属。发布验收另需确定试用范围、业务边界和验收集，不以当前几道开发题代替。

## 8. 何时开发自动化脚本

人工完成一轮标注、字段和口径稳定后，再实现自动化：

- 先自动化真实应用调用、会话 ID 传递、原始结果保存、失败记录和汇总。
- 字段完整性、计数和公式用确定性检查；语义正确、资料支持不能只靠关键词匹配。
- 引入 LLM 评审时，固定评审模型、Prompt 和版本，保存真实评审输出，并与人工标注对照。
- 现有 `scripts/evaluate_dify_retrieval.py` 只评测召回，不会生成答案，不能作为本 SOP 的生成评测入口。

## 9. 本项目 API 执行入口

已固定 [stack-generation-v0.json](../data/evaluation/stack-generation-v0.json)：四道独立单轮与一组两轮，共六次请求。历史标注见[记录](生成评测记录.md)，不得代填新运行结果。

1. 在项目本地 `.env` 填写 `DIFY_APP_API_KEY`。来源为应用“访问 API → API 密钥”，知识库 Key 不可替代；不把 Key 发到聊天或提交 Git。
2. PyCharm 打开 [evaluate_dify_generation.py](../scripts/evaluate_dify_generation.py)，右键 Run。默认真实调用当前已发布应用；缺少 Key 时启动失败，不创建伪结果。
3. 运行前保存并核对完整配置快照，可在 Parameters 传入 `--snapshot 相对路径/config.json --label baseline-v1`。未核对快照时不能声称配置已冻结。快照只含可分享配置，不能含凭据。
4. 脚本打印 `runs/dify-generation-*` 目录；每轮保存请求和完整 Dify 响应，后者包括 API 返回的引用与用量，但不是 Provider 原始 HTTP Trace。结果及时写入 `results.json`；不自动重试，失败后的同题多轮跳过并保留。
5. 对照 `cases.json`、`*-response.json` 和可获取的实际上下文填写 `review.csv`。质量维度使用 `pass/fail/pending/na`；`overall` 仅用 `pass/fail/pending`，通过或不通过必须在 `reason` 写证据，`reviewer` 写标注者。缺完整上下文时 source 保留 pending，不把候选引用当作模型已读取的全文。
6. 在 [summarize_generation.py](../scripts/summarize_generation.py) 的 Parameters 填运行目录，Run。它只汇总人工 overall，不猜测语义；失败与跳过单独计数，pending 不计为通过。

命令行等价入口（从项目根目录）：

```shell
.venv/bin/python scripts/evaluate_dify_generation.py --label baseline-v1
.venv/bin/python scripts/summarize_generation.py runs/实际运行目录
```

`latency_s` 为客户端 blocking API 完整等待时间，不是首 Token 延迟或纯模型耗时。脚本当前只允许本机 Dify；不支持远程凭据发送。相同脚本可用于单项优化后的回归，但必须记录新的配置与 label。
