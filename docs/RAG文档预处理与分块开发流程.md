# RAG 文档预处理与分块：开发流程与验收方法

## 1. 环节定位

**文档预处理与分块**属于 RAG 的数据摄取与索引构建流程（Ingestion Pipeline），负责把原始资料转换成可追溯、适合检索的知识片段。

```text
数据摄取与索引构建：
原始资料 → 解析 → 清理与规范化 → 分块 → Embedding → 索引存储
                              ↑       ↓
                              └─ 分块预览与检查

在线问答：
用户问题 → 问题 Embedding → 检索知识片段 → LLM 生成带来源的回答
```

本文主要讨论解析、清理、分块，以及这几个模块的开发和验证方法。Embedding 的调用与输出校验见 [BGE-M3 接入与向量化验证](向量检索演示原理.md)。

**开发期反复检查和调整策略；运行期按照已经确定的策略处理文档。** 不需要让每篇新增文档都经历人工试错，但异常文档应有明确的失败或人工复核入口。

## 2. 模块职责与数据产物

### 2.1 数据处理模块

| 模块 | 输入 → 输出 | 主要职责 | 验证重点 |
|---|---|---|---|
| 获取 | 数据源 → 原始文件与来源信息 | 固定来源、版本及访问范围 | 文件完整、来源可追溯 |
| 解析 | 原始文件 → 正文及结构信息 | 提取标题、段落、表格、代码；必要时执行 OCR | 有效内容是否被正确提取、顺序是否正确 |
| 清理与规范化 | 解析结果 → 规范化文档 | 处理模板残留、页眉页脚、无效引用、空白和重复内容 | 噪声减少，事实、条件和结构仍保留 |
| 分块 | 规范化文档 → 分块集合 | 按结构与长度约束组织可检索单元 | 语义边界、完整性、长度及来源映射 |
| 向量化与索引 | 分块集合 → 向量及索引记录 | 建立知识片段与向量、元数据的对应关系 | 数量与身份一致、输出有效、索引可查询 |

这是逻辑职责划分，不要求拆成多个服务。小型自研项目可以在同一进程中实现清晰的函数或模块边界，出错时能够定位到具体阶段即可。

### 2.2 原文、导入稿和分块的关系

- **原文**：来源内容的固定快照，保留来源 URL、版本、许可与文件校验值。处理过程中不覆盖。
- **解析结果**：文件解析出的正文和结构；可以是文本，也可以是含标题、表格、代码等元素的中间表示。
- **导入稿**：面向当前实验策略整理出的可处理资料，例如规范化 Markdown。它是原文的派生产物，不是新的权威来源。
- **分块**：由导入稿或规范化结构生成的检索单元，关联所属文档、来源位置与处理版本。
- **索引记录**：保存分块正文、向量和必要元数据，使检索结果可以还原到资料。

导入稿在手动 Dify 实验中可以是一个独立文件；自研系统也可直接传递规范化文档对象，不必为每个中间步骤都生成文件。保留足以复现输入、配置和关键输出的证据即可。

不要直接人工修订某次分块结果却不记录规则。否则下次重新处理同一资料时，结果可能恢复成旧状态。

### 2.3 最小数据契约

建议使用以下信息关联处理链路；字段名为设计建议，不代表当前项目已经实现：

```text
文档：document_id、source_uri、source_revision、source_hash
处理：pipeline_version、parser_version、cleaning_version、chunking_config
分块：chunk_id、document_id、text、section_path、source_locator
索引：chunk_id、embedding_model_revision、index_version
```

`source_locator` 可以是页码、章节、原文行范围或段落标识，取决于解析器能力。经过清理后的位置不能直接当作原文位置；无法精确映射时应说明定位粒度。父子分块还需保存父子关联。

`chunk_id` 应在同一次处理与索引链路中保持一致。分块策略变化后可以生成新 ID，但必须能通过文档和处理版本区分新旧结果。

## 3. 开发流程：两层验证循环

### 3.1 第一层：预览检查内容与边界

```text
选取代表性资料并固定原始版本
  → 解析与清理
  → 使用基线分块策略
  → 预览正文和分块
  → 记录具体问题并归因
  → 只调整相关规则或参数
  → 对同一资料重新预览
```

预览要同时看到完整分块内容、块序号、长度、所属章节及来源。只展示分块数量和几行摘要，不足以判断代码、表格和步骤是否完整。

| 预览现象 | 优先排查 | 调整方向 |
|---|---|---|
| 正文缺页、表格顺序错乱 | 解析 | 更换解析策略，检查 OCR、布局和表格提取 |
| 图片路径、模板标记独立成块 | 内容清理 | 识别无效引用与模板语法，保留必要语义和来源 |
| 语言标签与代码分离 | 结构识别与分块 | 保留代码块及语言归属，避免将标签作为独立正文 |
| 操作步骤与适用条件分离 | 语义边界 | 按章节、步骤组分块，或对照父子模式 |
| 大量重叠或无关主题混在一块 | 分块参数 | 检查重叠范围、长度限制和分隔符 |

不把所有问题都归因于分块长度。缺失的正文不会因为增加重叠而恢复，模板残留也不会因为换 Embedding 模型而消失。

每轮调整需要说明“发现了什么问题、改了什么、预期改善什么”。尽量一次只改变一个主要因素，保留前后结果，便于归因。

### 3.2 第二层：检索评测验证是否有用

预览通过后，执行真实向量化与索引，并用固定问题检查检索结果：

```text
候选分块策略 → 向量化与索引 → 固定问题检索 → 检查命中证据
       ↑                                      ↓
       └──────── 有明确失败原因时调整 ──────────┘
```

预览只能发现可见的内容和边界问题。检索评测才能判断：员工问题能否命中所需内容、返回上下文是否足够、错误样本是否减少。

评测问题应关联到原始文档和预期证据，不要只绑定某次生成的 `chunk_id`。分块策略变化后，正确答案可能位于不同块中，但原始证据仍应一致。

策略对比时固定资料版本、问题集、Embedding 模型和检索设置；只修改待比较的处理策略。可记录证据命中率、Top K 内容、返回上下文长度和失败样本。没有可靠标准证据时，先保留人工判断，不能用块数减少或相似度上升代替质量结论。

无答案问题用于观察误召回和后续拒答能力，不能把“总有一个第一名”当作答对。反复调参使用开发集；最终验收使用另行保留的问题，避免只适配已知样本。

检索权重的选择依据、测试与调优循环，以及 Hit@K、证据召回、排序、阈值和延迟指标的计算口径见 [召回测试记录：检索配置决策与迭代方法](召回测试记录.md#检索配置决策与迭代方法)。

## 4. 清理与分块策略的设计原则

### 4.1 清理必须保留业务含义

适合规则化处理的内容包括确定无意义的模板语法、重复导航、页眉页脚和多余空白。以下内容不能为了整洁而默认删除：

- 操作前提、适用版本、风险提示、例外和否定条件。
- 错误码、产品名、命令、参数和有业务价值的链接。
- 表格的列标题、代码缩进和段落所属章节。

图片仅为装饰时可清除无效引用；图片承载关键步骤时，需要补齐图片依赖、采用合适解析方式或明确资料覆盖缺口，不能让丢失信息后的文本被误认作完整资料。

多语言示例可按实验范围裁剪，但要记录范围变化。例如只保留 Python 示例后，不再声称该导入稿能回答其他语言的实现问题。

### 4.2 先保结构，再满足长度限制

优先按标题、段落、步骤组、表格和代码块组织内容，再处理超过长度限制的部分。代码和表格也可能过长，不能无限保留在同一块；拆分时需要携带函数归属、表头等必要上下文。

最大长度是上限，不代表每块都应达到该长度。短块也可能有效，例如完整的错误码解释。应重点识别没有独立语义的碎片，而非把所有短块都删除。

字符数与 Token 数是不同约束：分块工具可能按字符计数，Embedding 和生成模型受 Token 上限约束。配置必须标注单位，并在模型调用前检查实际输入，禁止把字符数当作 Token 数。

重叠用于缓解边界丢失，过多会增加存储和重复召回。父子模式则把匹配范围与返回上下文范围分开，两者都需要真实检索验证，不能仅凭名称判断更好。

## 5. 当前《栈》文档案例

### 5.1 已观察到的结果

2026-10-15，使用 Dify 直接创建入口上传[原始 stack.md](../data/knowledge/hello-algo-v0/documents/stack.md)，查看分块预览：

- 通用模式，分隔符为 `\n\n`。
- 最大长度为 1024 **字符**，重叠长度为 50 **字符**。
- 页面显示 124 个预估块；这不是已完成索引的块数。
- 图片相对路径成为独立块，`"Python"` 标签成为独立块，代码示例被拆开。

页面已选择高质量索引和 `bge-m3:latest`，但本次停在预览阶段，未点击“保存并处理”，不能据此认为完成了资料向量化或索引构建。

124 块本身不构成失败证据；其中无意义的路径块、标签块以及缺少上下文的代码，才是本轮需要处理的具体问题。

### 5.2 下一轮候选处理规则

以下规则尚待用户确认及实际执行，不是已完成的清理结果：

1. 原文不动，另存导入稿，保留标题、来源、上游版本及许可信息。
2. 将语言选项模板转换为标准 Markdown 结构；本轮若仅保留 Python，明确标记语言覆盖范围。
3. 处理图片相对路径和未展开的源码引用；无法恢复的实质内容记为缺口，不编造说明或实现代码。
4. 保留操作表格与代码结构，重新检查通用分块结果，再判断是否调整分隔符、长度或采用父子模式。
5. 预览通过后，确认执行向量化入库，再用围绕定义、操作、实现前提的问题做检索对照。

当前不一次性清理全部六篇文档。先用一篇确定规则，再用含有不同结构的资料检查规则是否适用，之后处理整批。

## 6. 自研模块与 Dify 操作的对应关系

| 开发环节 | 自研系统的实现入口 | Dify 中的对应操作 |
|---|---|---|
| 固定输入 | 原文快照、来源清单与版本 | 记录上传文件版本及来源 |
| 解析与清理 | Parser、规范化与清理函数 | 直接创建的解析和预处理；特殊需求使用导入稿或流水线提取节点 |
| 分块策略 | Chunker、结构规则与长度配置 | 分段设置；流水线中的分块器和知识库结构 |
| 预览检查 | 输出分块内容、长度与来源 | “预览块”；流水线的测试运行和输出检查 |
| 入库与评测 | Embedding、索引写入、检索与评分 | “保存并处理”、处理状态、召回／检索测试 |

并非所有清理规则都能在 Dify 直接创建的页面中表达。需要额外处理时，选择可复用的导入稿生成逻辑或知识流水线；由实际缺口决定，不必提前实现完整的自研摄取系统。

三个知识库入口及模板区别见 [Dify 知识库创建方式与流水线选型](Dify知识库创建方式与流水线选型.md)。

## 7. 日志、验收与停止条件

### 7.1 最小运行记录

每次处理记录文档身份、输入校验值、处理版本、分块配置、各阶段耗时和状态；记录异常、被排除的内容类别及无法恢复的依赖。分块结果记录总量、长度分布和超限情况，并提供问题块的定位信息。

这些统计用于发现异常，不是检索质量指标。例如块数突然上升可能来自结构破坏，也可能来自新增正文，需要结合内容判断。

本地实验可保存一次运行的配置、导入稿、分块结果和检索记录，不必先搭监控平台。已有 BGE-M3 向量化指标在[向量化验证文档第 7 节](向量检索演示原理.md#72-向量化环节的监控指标)单独说明。

### 7.2 分阶段验收

| 阶段 | 判定依据 | 不能据此声称 |
|---|---|---|
| 解析与清理 | 选定范围内有效正文保留；变化可解释；缺口有记录 | 资料业务事实一定正确 |
| 分块预览 | 无已知模板碎片；关键步骤、条件、代码和表格边界可解释；来源可定位 | 检索质量已经达标 |
| 索引构建 | 真实模型调用成功；向量与块关联正确；索引可查询；失败有记录 | 整体问答效果已经达标 |
| 检索评测 | 固定问题的预期证据命中情况及失败样本有记录，与基线可比较 | 生成答案、引用和转人工均已通过 |

当代表性资料的已知内容问题得到处理、分块满足已定约束时，结束预览循环，进入检索评测。只有具体失败样本或明确的新需求才驱动下一轮调整，不为了让预览“更整齐”无限优化。

### 7.3 配置冻结与更新

保留原文版本、清理规则、分块参数、模型身份、问题集版本和运行结果，形成可比较的基线。改变原文、清理或分块时，需要重新生成受影响分块并更新索引；更换不兼容的 Embedding 模型时，需要重建资料向量。

重复运行应避免累计重复索引，旧块应有更新或清理策略。生产环境还需讨论失败重试、部分成功和索引切换的一致性；当前实验先记录要求，不在本阶段实现这些能力。
